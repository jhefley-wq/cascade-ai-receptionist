# Durable Call Data Recovery Runbook

This branch is a **local recovery build only**. It must be reviewed and staged before any operator makes a Railway or Twilio change. Do not copy backups, call recordings, transcripts, or JSON snapshots into this repository.

## What changed

The service now stores calls in SQLAlchemy tables: `calls`, `transcript_lines`, and `call_status_events`. A call is created as soon as `/incoming-call` receives a `CallSid`; status callbacks append an audit event; each recognized transcript line is persisted as it is captured; and extraction output is saved against the same call. `pending_calls` is only a transient caller-ID lookup cache. PostgreSQL is the source of truth.

The dashboard (`/`), lead table (`/leads`), and receptionist control (`/toggle`) require HTTP Basic credentials from `ADMIN_USERNAME` and `ADMIN_PASSWORD`. If either is blank, those routes return **503** rather than exposing call data. Twilio routes do not use Basic auth, because Twilio needs to reach them directly.

## Configuration

Copy `.env.example` to a local secret store or configure equivalent Railway variables. Required production values are:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Railway PostgreSQL connection string. Legacy `postgres://` values are normalized for SQLAlchemy. |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Required Basic-auth credentials for operator routes. Use unique, long values. |
| `TWILIO_VALIDATE_SIGNATURES=true` | Enforces `X-Twilio-Signature` checks for `/incoming-call`, `/call-status`, and the Media Streams handshake. |
| `TWILIO_WEBHOOK_BASE_URL` | Exact public `https://host` origin registered for HTTP callbacks. |
| `TWILIO_MEDIA_STREAM_URL` | Exact public `wss://host/media-stream` URL emitted in TwiML and used for handshake validation. |
| `OPENAI_REALTIME_MODEL` | Defaults to `gpt-realtime-2.1`; set another approved model only after staging audio verification. |

`TWILIO_VALIDATE_SIGNATURES=false` is a local-development bypass only. A public staging or production service must use `true` and have `TWILIO_AUTH_TOKEN`, `TWILIO_WEBHOOK_BASE_URL`, and `TWILIO_MEDIA_STREAM_URL` configured. The validator uses Twilio's Python SDK and the exact externally configured URL, including the query string.

## Offline verification before staging

1. Create a fresh virtual environment and install `requirements-dev.txt` (which includes the production requirements plus the local HTTP test client).
2. Set `DATABASE_URL` to a disposable SQLite file or a dedicated non-production PostgreSQL database.
3. Run `python -m py_compile main.py storage.py import_snapshot.py` and `python -m unittest discover -s tests -v`.
4. Confirm `GET /`, `/leads`, and `/toggle` return 503 without administrator credentials, return 401 with bad credentials, and work only with valid Basic credentials.
5. Confirm an unsigned `/incoming-call` and `/call-status` request is rejected when `TWILIO_VALIDATE_SIGNATURES=true`. Test a correctly signed request generated by the Twilio SDK against the configured staging hostname.

These checks must use generated fixture values only; do not put real caller details into tests or logs.

## Staging plan

1. Provision a **separate** Railway project/service and a separate PostgreSQL database. Do not attach or alter the live database.
2. Configure all variables above in the staging service secret store. Give staging a stable HTTPS domain. Set `TWILIO_WEBHOOK_BASE_URL` and `TWILIO_MEDIA_STREAM_URL` to that exact domain before testing signature validation.
3. Deploy this reviewed branch to staging only. Let startup create the missing tables in the empty staging database. For future schema changes, use a reviewed migration rather than relying on `create_all`.
4. In a non-production Twilio setup or an isolated Twilio test number, configure `/incoming-call` and `/call-status` on the staging domain. Verify signed callbacks, a complete Media Stream call, transcript persistence, extraction persistence, status-history rows, dashboard authentication, and the inactive voicemail path.
5. Verify that normal INFO logs contain lifecycle events only, not caller numbers, transcript text, or extracted lead content.

## Optional legacy JSON import

Use an operator-controlled snapshot stored **outside** the repository:

```bash
DATABASE_URL='postgresql://...' python import_snapshot.py /secure/restore/leads.snapshot.json
```

The importer accepts either a JSON list or an object containing `leads` or `calls`. It is idempotent for records that have the same `CallSid`; records without one receive a deterministic `imported-...` identifier. It does not copy, retain, or back up the source file in this repository. Inspect row counts and samples directly in the destination database using approved access controls.

## Controlled production cutover (operator action only)

1. Back up the current live database/service through the operator's approved process and retain it outside Git. Record the current Twilio webhook configuration so it can be restored.
2. Provision or attach a production PostgreSQL database and set the production environment variables. Keep `TWILIO_VALIDATE_SIGNATURES=true`; do not use the local bypass. Verify an authenticated dashboard response before routing calls.
3. Deploy the reviewed artifact to the target service and confirm the health/startup logs show durable storage initialized. Do not change Twilio yet.
4. Change **only** the intended Twilio number's Voice webhook and Call Status Callback to the new exact public endpoints. Confirm a single controlled test call persists a call, status event, and transcript. Then monitor error rate and database connectivity.
5. If validation or audio fails, restore the saved Twilio webhook settings immediately. Do not delete call data while investigating.

No live deployment, Twilio reconfiguration, Railway mutation, Git commit, or Git push is performed by this recovery branch.

## References

Twilio signs webhook requests with `X-Twilio-Signature` and recommends using its SDK validator with all received parameters and the exact callback URL. See [Twilio Secure webhooks](https://www.twilio.com/docs/usage/webhooks/webhooks-security). Twilio also requires validation of the Media Streams `X-Twilio-Signature` handshake. See [Twilio Media Streams configuration](https://www.twilio.com/docs/global-infrastructure/firewall-configurations/media-streams-configuration).
